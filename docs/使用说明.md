# VR-Compose 使用说明

把 UE 渲染出的 **20 路方形相机序列帧**合成为 **360° 球形全景**（等距圆柱 / equirectangular），
直接输出可播的 MP4，或者输出无损的单帧母版。

**不需要安装 Python，也不需要另外装 ffmpeg** —— 都带齐了。

有两种发法，先看一眼你手上是哪种：

| 你拿到的是 | 怎么开始 |
|---|---|
| **一个 `VR-Compose.exe`**（单文件版） | 放哪儿都行，双击就开。ffmpeg 在它肚子里 |
| **一个文件夹**（里面有 exe、`ffmpeg.exe`、`ffprobe.exe`） | **整个文件夹一起用**，不要只把 exe 拷出来 —— 它要旁边那两个 |

单文件版的代价是**每次启动都要等**：它每次都把自己解包到临时目录（约 500 MB）之后才开始跑，
所以双击之后窗口不会立刻出来 —— **等着就行，不是卡死**。文件夹版是秒开（约 0.4 秒）。

---

## 一分钟上手

1. 单文件版：把 `VR-Compose.exe` 放到任意目录。文件夹版：解压整个文件夹。
2. 双击 **`VR-Compose.exe`**（单文件版要等它解包，见上）。
3. 「来源目录」点**浏览**，选到那个装着 `Camera1`…`Camera20` 的目录。
4. 看一眼「参数」，默认就是 8K / H.264 / 200 Mbps / 30 fps。
5. 点**开始**。进度、剩余时间、日志都在窗口里。

第一次跑之前建议先把「帧范围」改小一点（比如 `1656-1685`，30 帧），确认产物没问题再跑全长。

## 界面各处是什么

### 来源与输出

| | 说明 |
|---|---|
| **来源目录** | 装着 `Camera1`…`Camera20` 的那个目录。**留空**的话程序会在自己所在目录附近自动找 |
| **渲染名** | UE 输出的**文件名前缀**，比如 `L_Cathedral.1656.png` 的 `L_Cathedral`（代码和日志里叫 `stem`）。这是关卡/序列名，**跟左右眼没关系**（`L_` 是 UE 的 Level 前缀）。一组 `Camera*` 目录里只有一套渲染时它自动填好；放了多套才需要选，此时显示「— 请选择 —」，**必须自己选**，程序不会替你猜 |
| **帧范围** | `1656-2433` 这样的区间，也可以 `1656-`（到最后）、`-1700`（从最前）、`1,5,9`、或者 `all` |
| **输出位置** | 一个**目录**。留空则输出到程序所在目录 |

**关于帧范围的一个坑**：参考数据里除了 `1656..2433`，还有一张孤零零的 `0000` 帧。
把它算进去（也就是用 `all`）会让视频**开头跳一帧**。
所以程序默认帮你填的是**最后一段连续帧**，不是全部；日志里会说明它跳过了什么。

### 输出模式

| | 视频模式（默认） | 单帧模式 |
|---|---|---|
| 产物 | 一个 `.mp4` | 一个目录，里面一帧一个 `.png` |
| 尺寸 | 按「交付尺寸」（8K / 4K） | **按源自己的尺寸**（1920 的 tile → 7680×3840），不能改 |
| 压缩 | H.264 / H.265 **有损**压缩 | **无损** |
| 体积 | 8K 200 Mbps，778 帧约 2 GB | 8K 约 **39 MiB/帧**，778 帧约 **30 GB**（16 位约 101 GB） |
| 用途 | 交付、播放 | 归档、后续再加工、逐帧检查 |

切到单帧模式时，编码相关的参数会自动变灰 —— 那条路径上没有编解码器，所以也没有可调的东西。

### 参数

| | 说明 |
|---|---|
| **交付尺寸** | `8k` = 7680×3840（默认）、`4k` = 4096×2048。4K 是**先按 8K 拼好再降采样**得到的，不是直接拼小的 —— 直接拼小会走样。**4K 现在只是「想要小文件」的选项**（小 72%，画质降约 0.7–0.9 dB），不再是播放兼容性的必需 |
| **编码** | `h264`（默认，兼容性最好；**你的头显已确认能播 8K H.264**）/ `h265`（同码率画质接近，文件更小） |
| **码率档** | 8K：高 200 / 中 150 / 低 100 Mbps；4K：57 / 43 / 28 Mbps。实测 100 → 200 Mbps 只差 0.39 dB，**码率不是画质瓶颈** |
| **帧率** | 30（默认）/ 60 |
| **采样器** | `catmullrom`（默认，最还原，约 10 s/帧）、`bilinear`（快 2.8 倍，略软）、`nearest`（最快，有块状阶梯，**只适合预览**） |
| **母版位深** | 单帧模式才有。8 位够用；16 位保住重采样的亚灰阶精度，代价是文件大 3.4 倍 |

### 进度与日志

进度条在日志区**上方**，条上显示百分比和「已完成/总帧数」。
点开始之后它会先来回扫动（不确定态）—— 那是在发现来源、构建 warp 表、预检磁盘，
拿到总帧数之后才变成真正的百分比。

进度条下面一行是：**当前帧号、已完成/总数、当前分段、每帧秒数、相对旧流程 46.85 s/帧 的倍数、剩余时间**。

百分比同时写进**窗口标题**，所以窗口最小化之后在任务栏上也能看到进度。

日志区是深色那块。出问题时**先看这里**，它会把具体原因写出来。

## 取消与续跑

- 点**取消**：当前这一帧做完就停（8K 大约再等 10 秒）。**已经完成的部分全部保留**，不会留下半个坏文件。
- 想接着跑：把日志里那行 `output :` 的路径，**原样填回「输出位置」**，再点开始 —— 只会补没做完的部分。
- **注意**：如果「输出位置」留空让程序自动命名，每次跑都会得到一个**新的带时间戳的名字**，
  于是什么都不会复用（这就是时间戳的用意：每次跑是一份新产物）。**要续跑就必须自己指定路径。**
- 直接关窗口也等于取消，同样保留已完成的部分。

## 产物叫什么

```
视频：  L_Cathedral_0908_1751.mp4
单帧：  L_Cathedral_0908_1751\L_Cathedral_S_1656.png
                              L_Cathedral_S_1657.png
```

`<渲染名>_<月日>_<时分>`，本地时间。**同一分钟内跑第二次**会自动加后缀
（`L_Cathedral_0908_1751_2`），不会去接着写上一次的产物 ——
自动命名的原则是「每次跑都是一份新产物」，要续跑请自己指定路径（见上一节）。

## 播放器怎么知道这是个 360 视频

MP4 里写了一段 **360 元数据**（Spherical Video V2 的 `sv3d` box：等距圆柱投影、单眼、
无旋转）。播放器靠它把画面贴到球上；**没有这段元数据，同一个文件就只是一个 2:1 的宽画面**，
播放器会平铺显示。所以它是自动写的，不需要你勾任何东西。

想确认一个文件带没带，或者给**以前渲的老文件**补上：

```
VR-Compose.exe metadata L_Cathedral_0908_1751.mp4            # 只看
VR-Compose.exe metadata L_Cathedral_0908_1751.mp4 --write    # 补写
```

补写是**就地改**，只往文件里加 104 个字节，画面一个像素都不动（有测试逐字节比对过）。
已经带了的文件不会被写第二遍。

## 大概要跑多久

本机实测（Ryzen 9 7950X，32 线程）：

| | 每帧 | 778 帧 |
|---|---|---|
| 8K `catmullrom`（默认） | 约 10.1 s | 约 2.2 小时 |
| 8K `bilinear` | 约 3.8 s | 约 53 分钟 |
| 8K `nearest`（预览） | 约 2.1 s | 约 32 分钟 |
| 单帧 16 位 | 约 13.1 s | 约 2.8 小时 |

参考：**旧流程是 46.85 s/帧**，同样 778 帧要 10 小时。

内存峰值约 **24 GB**（8K，与总帧数无关）。机器内存紧的话可以让我加个开关把它降到约 10 GB，
吞吐只掉 4%。

## 出问题怎么看

| 现象 | 原因与处理 |
|---|---|
| **没有找到可用的来源集** | 目录结构不对。日志会逐条列出被拒绝的原因（比如「tile 非方形」「相机编号不连续」「各相机帧数不齐」），照着改 |
| **这个目录里有 N 套渲染** | 同一组 `Camera*` 目录里有多个文件名前缀，在「渲染名」里选一个。程序不替你猜，因为选错就是渲染了错的东西 |
| **装配不认识 / rig 未登记** | 相机数不是 20。目前只认 20 路那套装配，别的数量需要先反解朝向 —— 找我 |
| **几何门 FAILED** | 拼接几何不对（比如源数据的相机顺序变了）。程序会**立刻停下**而不是浪费几小时，把日志发我 |
| **磁盘空间不足，拒绝启动** | 输出盘剩余空间小于估算产物大小。换个盘，或者先清一下。单帧模式特别吃空间（见上表） |
| **窗口一闪就没了** | 说明启动就崩了。现在这种情况一般会**弹个报错对话框**；没弹的话，在 exe 所在目录开个终端跑 `VR-Compose.exe --version`，报错会打印在终端里 |
| **双击之后好久没反应** | 单文件版正常如此：每次启动都要解包约 500 MB。想秒开就用文件夹版 |
| **磁盘 C 盘涨了几百 MB** | 单文件版解包在 `%TEMP%`，正常退出会自己清；被强杀（任务管理器结束进程）就会留下 `_MEI*` 目录，手动删掉即可 |
| **窗口后面还有个黑色的命令行窗口** | **单文件版已修**（2026-09-09 之前有这个毛病）：它不再给自己开控制台，双击只出窗口。**文件夹版**双击时那个窗口还会**闪一两秒**再自己收起来 —— 那是有意留的，见下一节最后一段 |

## 「光度校正」这个勾选框是干什么的

渲染器（UE）里体积雾、曝光、运动模糊这些效果是**按每个相机视口单独算**的，相邻两台相机看同一个方向，
亮度会差几级。拼在一起就是雾里有淡淡的、tile 形状的色块，相机移动时接缝两侧模糊程度不同。
**默认勾上**，程序会把这种平滑的亮度差在混合前抹平；只动大面积的明暗，不碰边缘和纹理。
原本就一致的渲染基本不受影响（实测单个像素最多变 2 级）。想要和老版本逐字节一样的结果就把它取消。

日志里如果出现「overlapping tiles disagree beyond the warning tier」的 **WARNING**，意思是校正之后
相邻相机仍有一点不一致，但远不到装配错误的程度，作业会继续跑；只有差异大到只可能是相机装反、镜像反
（median 超过 2.5）时才会停下来。

## 顺便说一句：它也是个命令行工具

同一个 `VR-Compose.exe`，**带参数运行就是命令行**（不带参数才开窗口）。批量或者写脚本时有用：

```
VR-Compose.exe --source E:\22 discover
VR-Compose.exe --source E:\22 sequence --frames 1656-2433
VR-Compose.exe --source E:\22 sequence --frames 1656-1685 --out-format png
VR-Compose.exe metadata 某个已有的.mp4 --write
VR-Compose.exe --help
```

窗口里点开始，实际上就是让程序用你选的参数**再启动一次自己**去干活 ——
所以作业崩了也不会带走窗口，而且界面全程不卡。

**一个要知道的差别**：为了双击时不弹黑窗口，**单文件版没有自己的控制台**。
在 PowerShell 或 `cmd` 窗口里直接敲它，**命令立刻返回、什么都不打印**，程序其实还在后台算，
图或视频要过一会儿才出现（8K 一帧在没有显卡的机器上要半分钟以上）。看起来像「没反应」，其实是在跑。

**命令行请用文件夹版**（`VR-Compose\VR-Compose.exe`，保留控制台，会等它跑完、结果直接打印）。
手边只有单文件版时，把输出重定向到文件，跑完再看：

```
VR-Compose.exe --source D:\数据 frame --frame 100 --out D:\test.png > D:\test.log 2>&1
```

## 已知的限制（都是源数据决定的，不是软件的问题）

- **源是 8 位 PNG**，这是画质硬上限。上游改成 16 位或 EXR 才能突破。
- ~~**8K H.264 不能硬解，头显放不了**~~ —— **这条作废**：你已经在目标头显上确认能播
  8K H.264（2026-09-09）。所以 8K + H.264 就是可以交付的默认组合，
  `4k` 只是「想要小文件」时的选项（小 72%，画质降约 0.7–0.9 dB）。
  注意这条只对你那台设备成立，换设备要重新确认。
- **交付规格要求 4:2:0 色度**，这是规格锁死的，不是编码器没调好。
  实测它本身花掉约 **2.4 dB**（原先记的 4.3 dB 里有一多半其实是我们**量它的方式**带来的，
  已查清并更正）。四种自己做色度下采样的方案都试过（线性光、正确取样位置、抖动），
  最好的一种只赢 0.1 dB，不值得为它多一条颜色路径 —— 所以没改。
- **如果在某个播放器里看着整体偏暗**（大约 1/255，肉眼基本看不出来）：那是播放器自己的
  YUV→RGB 那一步，不是文件的问题 —— 文件里没有这个偏移，我们逐帧量过。ffmpeg 自己那条
  转换路会引入它，头显里常见的 GPU 渲染路一般不会。
- **极区（天顶/天底）比赤道软**：equirect 网格在极点要求的采样密度，任何针孔相机都给不出来。
  已经用更好的插值把它改善过，但物理上限还在。
